# C4 Model — Referência

O C4 Model (Simon Brown) é uma abordagem para visualizar e comunicar arquitetura de software em quatro níveis de abstração progressiva. Cada nível responde a uma pergunta diferente e é direcionado a um público diferente.

---

## Os 4 Níveis

### Nível 1 — Context (Sistema)
**Pergunta:** O que o sistema faz e quem o usa?
**Público:** Stakeholders não técnicos, sponsors, product owners
**Conteúdo:** O sistema em foco + atores externos (usuários, sistemas externos) + relações de alto nível

```
[Usuário Pessoa Física] --> [Sistema de Gestão Regulatória] --> [CVM / Bacen (externo)]
                                        |
                                        v
                               [Sistema de Email (externo)]
```

---

### Nível 2 — Container (Aplicações e Dados)
**Pergunta:** Quais são os grandes blocos tecnológicos do sistema?
**Público:** Times de desenvolvimento, arquitetos
**Conteúdo:** Aplicações, APIs, bancos de dados, filas, serviços — e como se comunicam

```
[Usuário]
   |
   v
[Web App: React] --> [API: Python/FastAPI] --> [Banco: PostgreSQL]
                              |
                              v
                     [Worker: Celery] --> [Fila: Redis]
                              |
                              v
                     [Serviço de Email: SMTP]
```

---

### Nível 3 — Component (Módulos internos de um Container)
**Pergunta:** Como um container específico está organizado internamente?
**Público:** Desenvolvedores do time responsável pelo container
**Conteúdo:** Módulos, classes, serviços internos, responsabilidades e dependências

```
[API: Python/FastAPI]
├── [Router: /regulatorio]
│     └── usa --> [RegulatorioService]
│                      └── usa --> [CVMScraper]
│                      └── usa --> [BacenScraper]
│                      └── usa --> [ResumoGenerator (Claude API)]
└── [Router: /notificacao]
      └── usa --> [NotificacaoService]
                       └── usa --> [EmailSender]
```

---

### Nível 4 — Code (Implementação)
**Pergunta:** Como um componente específico está implementado?
**Público:** O desenvolvedor que vai escrever ou manter aquele código
**Conteúdo:** Classes, interfaces, métodos — equivale a um diagrama UML de classes
> ⚠️ Raramente necessário; use apenas para componentes críticos ou complexos.

---

## Quando usar cada nível

| Situação | Nível recomendado |
|---|---|
| Apresentar o sistema para stakeholders | 1 — Context |
| Discutir escolhas tecnológicas (stack, infra) | 2 — Container |
| Revisar organização interna de um serviço | 3 — Component |
| Detalhar implementação de algo crítico | 4 — Code |
| Onboarding de novo desenvolvedor | 1 + 2 + 3 |
| Design review completo | 1 → 2 → 3 conforme necessário |

---

## Convenções C4 para diagramas ASCII/texto

- **[ ]** — elemento (sistema, container, componente, pessoa)
- **-->** — relação/dependência (adicione label quando necessário: `--> [usa REST]`)
- **Indentação** — hierarquia interna (componentes dentro de um container)
- **Legenda opcional** no final do diagrama para tipos de elemento

### Exemplo de legenda
```
Legenda:
  [Nome] (Tipo: Container | Tecnologia: Python/FastAPI)
  [Nome] (Tipo: Database | Tecnologia: PostgreSQL)
  [Nome] (Tipo: Person | Externo: não)
```

---

## Princípios de uso

- **Um diagrama por nível** — não misture abstrações no mesmo diagrama
- **Mostre apenas o que importa** — C4 não é UML exaustivo; omita detalhes irrelevantes para o nível
- **Explique as relações** — o label da seta é tão importante quanto os boxes
- **C4 complementa, não substitui** — use junto com Fowler (padrões) e Falácias (riscos)
